# BMAD Idea Launcher Architecture Memlog

**Workspace:** `_bmad-output/planning-artifacts/bmad-idea-launcher-architecture`  
**Scope:** BMAD Idea Launcher MVP system architecture  
**Purpose:** Architecture spine for single-screen idea generation web app  
**Altitude:** Initiative → MVP → Implementation  
**Status:** Open (ongoing decisions as implementation discovers gaps)

---

## Decisions Log

### decision | AD-1: Prompt-Driven, Stateless Generation

- **Context:** PRD emphasizes quick, repeatable first-step ideation. User should enter prompt and immediately see results.
- **Decision:** Each generation starts fresh; no prompt caching or auto-fill of previous attempts.
- **Binds:** Every flow validates input, calls LLM, renders new cards, clears prior results unless saved.
- **Prevents:** Accidental re-generation of stale ideas; user confusion between new intent and app memory.
- **Rationale:** Keeps state simple, aligns with UJ-1 (quick iteration), supports multiple experiments in one session.

---

### decision | AD-2: Exactly Three Ideas per Generation

- **Context:** PRD feature FR-2 requires "exactly three starter ideas"; design-thinking templates typically use three concepts.
- **Decision:** Enforce hard constraint: always three cards, no more, no fewer.
- **Binds:** LLM call + response handling must guarantee exactly three items.
- **Prevents:** UI layout surprises, card count drift, rendering complexity.
- **Tradeoff:** Less flexibility for users who want more or fewer ideas, but clarity trumps edge cases for MVP.
- **Fallback:** If LLM returns <3, pad with templates. If >3, truncate & log warning.

---

### decision | AD-3: Favorite State Ownership & Persistence

- **Context:** PRD feature FR-5 requires persistent favorite state across page refreshes; no backend persistence implied.
- **Decision:** Browser `localStorage` is canonical store; server does not manage favorites.
- **Binds:** Client reads/writes favorite state to `localStorage` on every toggle; no sync with server.
- **Prevents:** Server-side state complexity, user account requirements, database schema inflation.
- **Tradeoff:** Favorites are per-device, per-browser (no cloud sync). MVP scope accepts this.
- **Rationale:** Simplest, most portable solution for single-session artifact. Aligns with "learn BMAD in 1–2 hours" goal.

---

### decision | AD-4: Single-Screen, No Navigation

- **Context:** PRD feature FR-6 mandates "single-screen layout"; user journey UJ-1 shows all interactions on one view.
- **Decision:** Entire flow (prompt, generate, results, favorite) on one route. No modal dialogs, tabs, or page transitions.
- **Binds:** DOM structure is single tree; all content conditionally visible (CSS, JS state).
- **Prevents:** Navigation confusion, broken browser back button, lost context on nav.
- **Rationale:** Reduces cognitive load, aligns with MVP simplicity, enforces tight UX focus.

---

### decision | AD-5: Responsive Layout Constraint

- **Context:** PRD feature FR-7 requires responsive behavior at desktop and mobile widths without clipping or horizontal scroll.
- **Decision:** Mobile-first CSS; adapt to breakpoints (≤600px, 601–1000px, >1000px).
- **Binds:** All controls tappable, all content visible at 375px width (common mobile).
- **Prevents:** Broken mobile UX, poor accessibility, user frustration.
- **Test targets:** 375px (mobile), 768px (tablet), 1920px (desktop).

---

### decision | AD-6: Frontend Stack

- **Context:** PRD goal is "buildable in a single front-end session"; learning project assumes low complexity.
- **Decision:** Vanilla HTML/CSS/JavaScript, or minimal single-file framework (Alpine.js, Preact <50KB).
- **Binds:** No build step, no npm, no transpilation, no Node runtime on client.
- **Prevents:** Complexity creep (webpack, TypeScript, monorepos), deployment friction, scope expansion.
- **Rationale:** Aligns with "learn BMAD" ethos; any developer can read and modify the code in one sitting.
- **Note:** If a framework is used, must be CDN-loadable and <50KB minified.

---

### decision | AD-7: Backend Boundary & LLM Integration

- **Context:** Generation logic cannot run in browser (no local LLM in MVP scope); must call an external service.
- **Decision:** Thin, stateless backend exposes single POST endpoint `/api/ideas` (or equivalent).
- **Binds:** Backend accepts `{prompt}`, calls LLM, returns `{ideas: [{title, description}, ...]}` with exactly three items.
- **Prevents:** Scope creep into full backend (sessions, users, history); keeps MVP spirit intact.
- **Stateless rationale:** No per-user state, no shared mutable data, no long-lived sessions simplifies deployment and testing.

---

### decision | AD-8: LLM Provider Abstraction

- **Context:** OpenAI is a default choice, but the team may want to swap to Anthropic, Cohere, or a local LLM later.
- **Decision:** Backend implements provider abstraction; swap provider via environment variable at startup.
- **Binds:** Internal backend interface is provider-agnostic; frontend never knows the provider.
- **Prevents:** Tight coupling, fragility on API changes, vendor lock-in.
- **Rationale:** Minimal cost upfront; enables testing and experimentation later.

---

### decision | AD-9: Error Handling & Observability

- **Context:** Network failures, LLM timeouts, and API errors will happen; MVP must handle gracefully.
- **Decision:** User sees brief, friendly error message + retry affordance; errors are logged server-side.
- **Binds:** Error flow preserves user prompt; allows re-submission without loss of context.
- **Prevents:** Silent failures, raw API errors leaking to user, frustration on retry.
- **Logging:** Server logs errors (provider, timestamp, error type) for post-mortem debugging.

---

### decision | AD-10: Idea Card Data Model

- **Context:** Each idea must be concise and scannable (PRD FR-3 specifies "title and short description").
- **Decision:** Exactly two visible fields per card: `title` (max 60 chars) and `description` (max 200 chars).
- **Binds:** Backend enforces schema; frontend renders only these two fields.
- **Prevents:** Unbounded schema drift, layout surprises, rendering logic complexity.
- **Optional fields:** Timestamp, UUID, source (used internally but not shown to user).
- **Rationale:** Fixed schema makes testing, caching, and UI predictable.

---

### decision | AD-11: Favorite Toggle Semantics

- **Context:** PRD feature FR-4 allows marking ideas as favorites; FR-5 requires persistence across refreshes.
- **Decision:** Each card has boolean favorite state; a user can favorite multiple ideas in one generation.
- **Binds:** Favorite state is binary (not ranked); stored as array of `{title, description, generatedAt}` in localStorage.
- **Visual:** Favorited card is visually distinct (filled star, border highlight, or color change).
- **Prevents:** Ambiguity about what "favorite" means; loss of context on page reload.
- **Match logic:** On page load, compare incoming ideas to stored favorites by (title + description) equality.

## Assumptions

### [ASSUMPTION: OpenAI API is the LLM backend]

- **Rationale:** Widely available, fast, cost-effective for MVP.
- **Mitigating factor:** AD-8 (LLM Provider Abstraction) lets swapping out later without re-architecture.
- **Revisit when:** Team evaluates other providers or local LLM feasibility.

### [ASSUMPTION: No authentication required for MVP]

- **Rationale:** Simplifies backend, no user accounts, public demo artifact.
- **Mitigating factor:** SPA is stateless; easy to add auth later if multi-user version is planned.
- **Revisit when:** Requirements call for per-user favorites or collaboration.

### [ASSUMPTION: Frontend runs in modern browsers only]

- **Definition:** ES2020+, localStorage, flexbox/grid, fetch/async-await support.
- **Rationale:** Aligns with current dev-time practices; no IE11 or legacy burden.
- **Revisit when:** Enterprise or legacy browser support becomes a requirement.

### [ASSUMPTION: Prompt templating is not applied by the backend]

- **Meaning:** User's prompt is sent directly to LLM; no hidden instructions, no domain-specific injection.
- **Rationale:** Keeps backend simple; ideas reflect user intent, not hidden framework.
- **Revisit when:** Post-MVP quality improvements might benefit from prompt engineering.

## Open Questions

### [OPEN] How to handle LLM returning fewer than three ideas?

- **Context:** If OpenAI or another provider returns only one or two ideas, do we pad with fallback templates, repeat ideas, or show an error?
- **Impact:** Affects reliability of "exactly three ideas" invariant.
- **Who decides:** UX designer + implementation team during story breakdown.
- **Options:**
  1. Pad with generic fallback template (e.g., "Consider this angle: ...").
  2. Repeat the strongest idea.
  3. Show error and ask user to retry (breaks AD-2).
- **Recommended:** Fallback template; preserves user experience and AD-2 invariant.

---

### [OPEN] Which Node/Python framework for the backend?

- **Context:** AD-7 specifies thin backend but doesn't name the framework (Express, FastAPI, etc.).
- **Impact:** Affects dev time, deployment footprint, team familiarity.
- **Who decides:** Implementation lead + team preference.
- **Options:**
  1. Node.js + Express (lightweight, npm ecosystem).
  2. Python + FastAPI (modern, async-friendly, fast).
  3. Python + Flask (minimal, but less async-native).
- **Recommended:** Express (Node) for speed + ecosystem familiarity on BMAD teams.

---

### [OPEN] Should the app track generation history?

- **Context:** Currently no history tracking; each generation replaces prior results (unless favorited).
- **Impact:** Post-MVP feature; affects data model and UI.
- **Revisit when:** Post-launch feedback indicates users want to compare prior generations.

---

### [OPEN] What happens to favorites on browser cache clear or private browsing?

- **Context:** localStorage is per-browser, per-session. Private browsing typically clears storage on close.
- **Impact:** User frustration if they lose favorites unexpectedly.
- **Mitigating factor:** MVP scope accepts this trade-off; post-MVP could add export/save as JSON.
- **Revisit when:** Users report issues or feature requests surface.

## Decisions Triaged

### [Blocker: Resolved] LLM provider cost & availability

- **Issue:** OpenAI API has rate limits and costs; MVP must handle gracefully.
- **Resolution:** Backend implements retry logic + exponential backoff. Error message tells user to try again. Optional: cache-busting (dev time allows low-cost retry during testing).
- **Logged:** Covered by AD-9 (Error Handling).

---

### [Non-blocker: Deferred] Full idea management (edit, delete, search)

- **Issue:** Would double scope.
- **Decision:** Post-MVP feature; marked as out-of-scope in PRD (Section 5).
- **Deferred to:** bmad-create-epics-and-stories (v2 roadmap item).

## Technical Direction Notes

### Why Not Full Database + Backend?

- Complexity: user accounts, auth, persistence, migrations, ops.
- Cost: deployment burden, monitoring, scaling decisions.
- **MVP priority:** Learn BMAD in 1–2 hours; breadth over depth.

### Why Not Serverless (Lambda, Cloud Functions)?

- Simpler to reason about (traditional request/response, no cold start surprises).
- Portable (run locally, test offline, deploy anywhere).
- **Tradeoff:** Slightly more ops knowledge; but learning value outweighs minor scaling limitations for MVP.

### Why localStorage, Not IndexedDB or Service Worker Cache?

- Simplicity: localStorage is available in all modern browsers.
- Familiarity: most frontend devs know it.
- **Tradeoff:** 5–10 MB limit per origin (plenty for favorite cards). Post-MVP could upgrade to IndexedDB for richer offline.
