- (decision) [ADOPTED] Paradigm: layered monolith (presentation/static -> HTTP handler -> service -> provider adapter). Binds: whole app. Prevents: split into premature services for a single-screen MVP. Ratified from existing server.js (plain Node http module, no framework).
- (constraint) [ADOPTED] No web framework (Express etc.) — existing server.js uses Node core 'http' module directly. Binds: all HTTP handling. Prevents a builder introducing Express/Fastify and diverging from the established convention.
- (decision) AD: Idea Generation Service is implemented as a provider-adapter function called only from the server-side /api/ideas handler; the LLM API key is read from process.env server-side only and never sent to the client. Binds: FR-2, FR-2 NFR. Prevents: API key leakage to client code or ad-hoc key reads scattered across handlers.
- (assumption) [ASSUMPTION] LLM provider is Anthropic Claude (Messages API), matching PRD glossary's 'e.g. Claude' and this being a Claude Code / BMAD learning exercise. Open question #1 in PRD leaves provider unresolved -- adapter boundary (AD) makes the concrete provider swappable without violating the spine.
- (decision) AD: All state (prompt, three ideas, favorite index) is held only in browser memory (a single client-side state object in app.js) for the lifetime of the page; nothing persists server-side and no session/cookie mechanism exists. Binds: FR-1, FR-3, FR-4, PRD 7.1 session-only scope. Prevents: introducing a DB, session store, or server-side state that PRD explicitly puts out of scope.
- (decision) AD: Favorite selection is single-select and owned entirely client-side (index of the favorited card, or null); the server has no concept of favorites. Binds: FR-4. Prevents: two independently-built units disagreeing on whether favorite state lives client- or server-side, or supporting multi-select.
- (decision) AD: /api/ideas is the sole backend endpoint; POST body {prompt: string}, success response {ideas: [{title, description}, x3]}, error response {error: string} with 400 for empty/invalid prompt and 502/504-class mapping for provider failure/timeout. Binds: FR-2 consequences (inline error + retry, 30s target). Prevents: ad hoc response shapes between the fake stub today and the real provider call later.
- (constraint) [ADOPTED] Test convention: node's built-in 'node --test' runner (already wired in package.json), CommonJS modules throughout (server.js uses require/module.exports). No test framework substitution.

Confirmed via git show be00e36. Excluded from this spine's scope; flagged so a future builder doesn't wire it in by mistake.

- (decision) AD-5 amendment: adapter-level timeout fixed at 25s (under the PRD's 30s end-to-end target, leaving headroom for handler+network overhead); a timed-out or failed provider call maps to 504 { error }. - (decision) AD-6 (new): Handler/Adapter interface fixed -- adapter exported as module.exports.generateIdeas from lib/ideaService.js, signature (prompt: string) => Promise<Array<{title, description}>> exactly length 3, failures signaled ONLY by throwing (never a resolved {error} envelope); handler's single try/catch is the sole error path. Closes critical finding: two AD-2-compliant adapters could otherwise disagree on export name/signature/error-signaling and simply not interoperate.
- (decision) AD-5 tightened: exact status codes pinned -- 400 invalid request (bad JSON, non-string/empty/whitespace-only/>2000-char prompt), 504 provider timeout, 502 provider/network failure, 500 malformed provider response (including != 3 parsed ideas -- adapter must throw, never pad/truncate/fabricate to force conformance). Handler must wrap JSON.parse in try/catch (AD-1 forbids framework body-parser safety nets).
- (decision) AD-5 timeout ownership: server enforces the timeout via AbortController on the provider call fixed at 25s, always resolving 504 before any client-side timeout would fire; client fetch carries no separate abort/timeout of its own -- prevents double-dispatched LLM calls from independent client+server timeouts.
- (decision) AD-3 tightened: the prompt <input> is a controlled element -- every input/change event writes state.prompt, making it the always-current source of truth (not just captured at submit). Submitting a new prompt synchronously clears ideas and resets favoritedIndex to null before the fetch is dispatched, so no stale favorite/idea state from a prior request can render against a new one.
- (decision) AD-4 tightened: clicking the currently-favorited card toggles favoritedIndex back to null (deselect); clicking a different card moves the favorite to it (single-select, per existing AD-4).
- (decision) AD-6 amendment: adapter must never cache or memoize provider responses -- every generateIdeas(prompt) call is a genuinely fresh LLM call, even for a repeated identical prompt. Binds: PRD SM-C1 counter-metric. Prevents a future contributor 'optimizing' latency by caching and silently violating the PRD's explicit do-not-optimize metric.
- (decision) AD-5 amendment: client short-circuits on empty/whitespace-only prompt -- app.js must not issue POST /api/ideas at all in that case (PRD FR-2: 'does not trigger a call to the Idea Generation Service'). Server-side 400 (AD-5) remains a defense-in-depth backstop, not the primary gate.
- (convention) Consistency Convention added: the favorite highlight must be conveyed by more than color alone (e.g. a distinct border plus an icon/label change), per PRD FR-4 accessibility consequence -- not just a background-color swap.
- (event) spine finalized
- (decision) AD-6 amendment: adapter throw taxonomy pinned -- thrown errors carry a .code property, one of 'TIMEOUT' | 'NETWORK' | 'MALFORMED'; handler maps code->status: TIMEOUT->504, NETWORK->502, MALFORMED->500, any uncoded/unknown throw->500. Closes gap: two AD-6-compliant adapters using different underlying HTTP clients (fetch vs axios) could otherwise use incompatible error discriminators, causing the handler to misclassify status codes.
- (decision) AD-3 amendment: the Generate button is disabled for the duration of an in-flight /api/ideas request; app.js does not dispatch a second request while one is pending, so no overlapping fetches or stale-response races are possible. Closes gap: two AD-3-compliant clients could otherwise allow double-submit, letting a stale response overwrite a fresher one.
- (decision) AD-6 amendment: the AbortController and its signal are owned and created inside the adapter itself (lib/ideaService.js), passed directly to the outbound provider HTTP call -- not a handler-side Promise.race, which would leave the outbound call running after 'timing out'. Makes the 25s timeout in AD-5 an actual abort of the network call, not just a settled promise.
