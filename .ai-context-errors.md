# Error & Exception Taxonomy

## Adapter Throw Codes (Architecture AD-6)

`lib/ideaService.js`'s `generateIdeas(prompt)` signals every failure by throwing — never by resolving an `{ error }` envelope. Thrown errors carry a `.code` property from this fixed set:

| `.code` | Meaning | Maps to HTTP status (AD-5) |
| --- | --- | --- |
| `'TIMEOUT'` | The adapter's own `AbortController` aborted the outbound provider call at 25s | `504` |
| `'NETWORK'` | The provider call failed before responding (connection refused, DNS failure, etc.) | `502` |
| `'MALFORMED'` | The provider responded, but output didn't parse into exactly 3 well-formed `{title, description}` entries | `500` |
| *(uncoded / unknown)* | Any thrown error without a recognized `.code` | `500` |

The handler's single `try/catch` around the `generateIdeas` call is the sole place this mapping happens — do not duplicate error-code logic elsewhere.

## Request Validation Errors

Handled entirely in the `server.js` handler before the adapter is ever called (bad JSON, non-string/empty/over-length `prompt`) → `400`. See `.ai-context-api.md` and `.ai-context-security.md`.

## Retry Policy

- `504`/`502` (provider/network trouble): the PRD's retry model is a single **user-initiated** retry (re-clicking `Generate ideas`) — no automatic retry-with-backoff inside the adapter or handler (PRD §5.1 Out of Scope).
- `500` (malformed output) and `400` (validation): never auto-retried — the adapter must not pad/truncate/fabricate to force a `MALFORMED` case into looking successful, and the client must not resubmit an invalid prompt automatically.

## Customer-Facing Messages

- Never expose stack traces, internal `.code` values, or implementation details in the `error` string returned to the client.
- Keep error text short and actionable (matches the existing `public/app.js` pattern, e.g. `"Ideas couldn't generate. Try again."`).
